## Project summary

The program simulates coders sitting in a circular arrangement.

* Each coder must be represented by a POSIX thread.
* There is one USB dongle between each pair of coders.
* A coder needs both adjacent dongles simultaneously to compile.
* Coders repeatedly compile, debug, and refactor.
* Each dongle must be protected using a mutex.
* A condition variable may be used to manage waiting.
* After release, a dongle remains unavailable during its configured cooldown.
* Requests for a dongle must follow either FIFO or EDF scheduling.
* A separate monitor thread must detect burnout precisely.
* Output must be serialized.
* Global variables are forbidden.
* All allocated memory and initialized synchronization objects must be cleaned correctly.
* The program must compile with:

```bash
-Wall -Wextra -Werror -pthread
```

The program receives:

```text
./codexion number_of_coders time_to_burnout time_to_compile time_to_debug time_to_refactor number_of_compiles_required dongle_cooldown scheduler
```

The scheduler must be exactly:

```text
fifo
```

or:

```text
edf
```

For FIFO, requests must be served in arrival order.

For EDF, the coder with the earliest burnout deadline has priority:

```text
deadline = last_compile_start + time_to_burnout
```

Equal EDF deadlines must use a deterministic tie-breaker.

The subject requires a custom priority queue implemented as a binary heap. I cannot use a standard-library priority queue.

The simulation stops when:

1. A coder burns out; or
2. Every coder completes at least `number_of_compiles_required` compilations.

A coder burns out if they do not start compiling before their deadline. At the beginning, the deadline is calculated from the simulation start time.

A burnout message must be printed no later than 10 milliseconds after the actual burnout.

Required logs include:

```text
timestamp_in_ms X has taken a dongle
timestamp_in_ms X is compiling
timestamp_in_ms X is debugging
timestamp_in_ms X is refactoring
timestamp_in_ms X burned out
```

Two log messages must never become mixed on the same line, and normal actions must not be logged after the terminal burnout message.

## Important design questions

Pay special attention to the following difficult parts.

### Protecting shared state

Create a protection table containing:

```text
Shared field or invariant | Protecting mutex | Writers | Readers
```

Every shared field must have a clearly identified mutex. Never suggest using `volatile` as a replacement for synchronization.

### Condition variables

For every condition variable, identify its predicate explicitly.

Explain:

* why the predicate is checked while holding a mutex;
* why `pthread_cond_wait` and `pthread_cond_timedwait` must be inside a `while` loop;
* when to use `pthread_cond_signal`;
* when to use `pthread_cond_broadcast`;
* how blocked threads wake during shutdown.

### Time management

Explain which clock should be used and why.

Do not mix timestamps from different clocks.

Clearly distinguish:

* simulation-relative timestamps;
* action durations;
* absolute deadlines;
* burnout deadlines;
* dongle cooldown deadlines.

Make sure the proposed design can detect and log burnout within the required 10 milliseconds.

### Two-dongle acquisition

Do not treat this like a simple mutex-locking exercise.

The design must explain:

* when a coder enters each dongle’s waiting heap;
* how the coder becomes eligible for both dongles;
* whether a coder may hold one dongle while waiting for the second;
* how circular waiting is prevented;
* how FIFO/EDF priority is preserved;
* how a pending request is cancelled during shutdown;
* how a coder is removed safely from both heaps;
* how cooldown is respected;
* why the protocol cannot duplicate a dongle;
* why the protocol cannot deadlock;
* under what conditions starvation is prevented.

If several architectures are possible, compare them first and explain their trade-offs. Recommend the simplest architecture that fully satisfies the subject. Do not select an architecture only because it resembles the classic dining-philosophers solution.

### FIFO and EDF heap

The heap implementation must support deterministic behavior.

For FIFO, the key should preserve request arrival order using a monotonically increasing sequence number.

For EDF, compare:

1. Burnout deadline
2. Arrival sequence
3. Coder ID

Explain whether request removal or cancellation is required and how to preserve the heap invariant after removal.

### Monitor thread

The monitor must read coder timestamps and compile counters without data races.

Compare simple polling with deadline-driven waiting. Recommend the method that can reliably satisfy the precision requirement.

Explain exactly:

* when `last_compile_start` is initialized;
* when it is updated;
* when a coder is considered burned out;
* how the earliest deadline is found;
* how the monitor sleeps;
* what events wake the monitor;
* how the terminal stop state is set only once;
* how the burnout message is serialized;
* how messages after burnout are prevented.

### Special cases

Explicitly handle:

* One coder and one dongle
* Two coders
* Equal EDF deadlines
* Zero or invalid numeric arguments
* Integer overflow during parsing
* Thread creation failing halfway
* Mutex or condition initialization failing halfway
* Shutdown while waiting for a dongle
* Shutdown during cooldown
* Shutdown while compiling, debugging, or refactoring
* All coders reaching the required number simultaneously
* Parameters that make avoiding burnout impossible
